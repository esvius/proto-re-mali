# Prototype (2009) PC: результаты этапа 1 (инвентаризация)

Цель: Steam-сборка 19788432.
- `prototypeenginef.dll`: SHA-256 `d331be205bdde99897952ee88261ab7e63c5c65e36a4660e2a367886a3537071`
- `prototypef.exe`: тонкий хост

Источники: импорты/экспорты (`winedump`), строки (`strings`), MSVC RTTI.
Ghidra-анализ через REA ещё не завершён.

## Архитектура запуска (наблюдение)
`prototypef.exe` только создаёт окно Win32 и цикл сообщений, затем делает `LoadLibraryA` на движок
и вызывает экспортируемые функции:
`EngineInitialize`, `EngineService`, `EngineTerminate`, `EngineKeyboardService`,
`EngineMouseService`, `EngineWindowFocus` (адреса экспорта: 0x0085EFB0, 0x0085EB20, 0x0085E340, …).
→ Хост-слой для Android = собственная реализация этих 6 точек входа поверх SDL.
→ Для hook-and-replace удобно: свой exe-хост может грузить оригинальную DLL и ставить хуки до `EngineInitialize`.

## Компилятор
MSVC 2005 (MSVCR80), x86, внутренний путь сборки `atg\engine\code\...`.

## Встроенные сторонние библиотеки (наблюдение по строкам)
- **Scaleform GFx** (`G*`-классы в экспорте, `GFx*` RTTI, обёртка `scaleformp3d`): все меню и HUD
  (`art\hud\proto*.gfx`: protomainmenu, protohud, protooptions, protosaveload…).
  Проприетарная → **заменять**. Вариант: open-source Flash-плеер с поддержкой AS2
  (например Ruffle, Rust, MIT/Apache) + реализация расширений Scaleform и callback'ов
  `CustomCallbackHandler`/`TextBibleInterfaceHandler`. Проверить версию GFx и AS2/AS3 по самим .gfx.
- **zlib 1.2.3** (`Decompressor_Zlib`) → системный zlib.
- **libpng 1.2.8** → libpng/stb_image.
- **Lua 5.1**, скрипты — **байткод** (`scripts/frevents.lua` начинается с `\x1bLuaQ`):
  заголовок: little-endian, int=4, **size_t=4**, instruction=4, **lua_Number=4 байта, float**
  (нестандартная сборка `LUA_NUMBER=float`). Для arm64: свой загрузчик чанков с 32-битным size_t,
  либо декомпиляция байткода и перекомпиляция под 64 бит.
- Физика — **собственная** `ravenphysics` (Havok не найден) → декомпилируем.
- Bink — внешняя DLL, не внутри движка.

  по порядку смещений: `scripts\frevents.lua` из архива побайтно совпал с копией на диске.

- **`.rz`** = заголовок 16 байт `{"RZ\0\0", 0, unpacked_size, 0}` + один zlib-поток; на 80 выборочных файлах
  из всех архивов ошибок нет, внутри во всех случаях Pure3D (`P3D\xff`).
- Содержимое: `0Xaudio.rcf`: 14 614 `.p3d`, звук упакован в Pure3D-чанки; `0Xwoi.rcf`/`movies.rcf`: Bink 1
  (`BIKi`, FFmpeg поддерживает) + `.p3d`; `art.rcf`: 363 `.gfx` (**`GFX\x08` = Scaleform на базе SWF 8,
  ActionScript 2** → совместимо с AS2-рантаймами вроде Ruffle), 2219 `.p3d`, 19 `.dds`;
  `cells.rcf`: 520 ячеек мира `.p3d`.
- В `scripts.rcf` только 2 Lua-файла, значит скрипты миссий лежат внутри Pure3D-чанков: следующая цель — парсер P3D.

## Pure3D (проверено `tools/p3d.py`)
- Файл: `{0xFF443350, 12, file_size}`; чанк: `{id, data_size, total_size}`, дочерние чанки идут после
  `data_size`. Все 520 файлов `cells.rcf` разобраны без ошибок.
- Самые объёмные чанки в `cells.rcf`: `0x00010012` (~611 МБ, предположительно вершинные данные),
  `0x00019002` (~569 МБ, данные текстур), `0x07021007` (~52 МБ).
- `0x07f00000`/`0x07f00001`: метаданные объектов (`proto::StatsManager(1)`, `engine::SkuInfo(1)`)
  с блоком `META`, то есть сериализация через метатипы `content\src\meta`.
- **`0x20000702`: сериализованные объекты формата `fig0` (версия 5).** В 86 из 1542 таких чанков в
  `art.rcf` внутри объекта лежит **Lua 5.1-байткод** (миссии `art\missions\*\*_fig.p3d`, NIS-катсцены
  `art\nis\*_fig.p3d`, пакеты `art\packages\missions\*`). Скрипты миссий — это поля
  fig-объектов, а не отдельные файлы. Для порта нужен загрузчик `fig0` + Lua 5.1 (float, size_t=4).

  `0x00018200–02` (текст), `0x00019002` (текстуры: шрифты/надписи), `0x0001100c`.

- Вывод для порта: рендер текста обязан поддерживать **UTF-8**, шрифтовые атласы берутся из пропатченного
  `art.rcf`. Оверлей = пропатченные пользователем архивы (или извлечённые из них записи) поверх оригинала.

## Файловая система: хеш имён (восстановлено и проверено)

  `FUN_106502c0(base, count, key, stride)` (найден наблюдателем за памятью `PROTORE_PROBE=watchdir`).
- `CementLibrary::vfunction8` (открытие по готовому ключу) до главного меню не вызывается.

## CementLibrary: заголовок и состояние (восстановлено и проверено)
- `CementFileRangeInit` (0x00651130, thiscall, ret 20h): заполняет диапазон файла (0x2c байт), абсолютное
  смещение = смещение записи + базовые смещения всех вложенных дисков (слот 32 vtable диска, вызывается дважды
  на уровень); слот 0 (ссылка) в начале, слот 16 в конце; 8-й аргумент не используется.
- `CementLibraryValidateHeader` (0x006503c0): заголовок `.rcf` копируется в объект с `+0x28`;
  сигнатура 24 байта `ATG CORE CEMENT LIBRARY\0`; версия: `+0x48` = 2, `+0x4b` ≠ 0, `+0x49` (минорная,
  она же «компактные записи») < 2, `+0x4a` = 0; для минорной 0 требуется `+0x18 == +0x1c`.
- `CementLibrarySetState` (0x00650410, ret 4): состояние в `+0x24`; ожидающий объект завершения `+0x70`
  получает слот 3 (аргумент из `+0x74`) и слот 1, затем оба поля обнуляются.
- Дифтесты: 14 132 проверки, 0 расхождений; с 9 хуками игра работает до меню.

## core::File (восстановлено и проверено)
Раскладка (0x174): `+0x04` подобъект-замок (слот 0 lock, 1 unlock), `+0x08` ссылки, `+0x0c` диск,
`+0x10` приоритет запросов, `+0x14` статус, `+0x18` незавершённые запросы, `+0x1c` CountedEvent,
`+0x24/+0x25/+0x26` событие создано / есть ожидающий / открыт, `+0x27` флаг, `+0x28` имя[256],
`+0x12c..+0x134` поля, `+0x138` подобъект (0x2c, обнуляется), `+0x16c` «открывать сразу», `+0x170` блок 0x800.
- Все операции асинхронны: запрос (`0x0064c4e0`, размер 0x0c–0x1c) + конструктор запроса + очередь диска
  (`0x0064feb0`) с приоритетом файла; при нехватке памяти в очередь уходит нулевой запрос, как в оригинале.
  «…и ждать» = слот операции + слот 21 (ожидание).
- Ожидание: опрос (слот 20 + обслуживание диска + Sleep(0)) или блокирующее (CountedEvent, счётчик 1).
- Пул файлов: мьютекс ФС `0x0127ca60`, пул `0x0127ca78` (слоты 18 выделить, 19 индекс, 4 освободить,
  11 перечислить, 1 освободить пул), таблица индексов `0x0127ca7c`, счётчик `0x0127ca80`.
- CountedEvent (Win32 manual-reset event + счётчик): Create/Destroy/Reset/Signal/Wait — платформенный слой.
- Не подменяемы (3–4 байта, логика повторена): open `0x0064e6e0`, name `0x0064e710`, no-op `0x0064e730`,
  priority `0x0064e740`. Не восстановлен: отладочный вывод открытых файлов при исчерпании пула `0x0064df50`.
- Дифтест: 11 групп сценариев, 0 расхождений; все 89 хуков установлены, игра работает до меню.
- Инструменты: `PROTORE_SKIP=<префикс>` (не ставить хуки группы); `disfn.sh` больше не путает адреса вида
  `1064e350` с числами в экспоненциальной записи.

## Статическая перекомпиляция x86 → C (прототип)
- `tools/recomp/recomp.py` (capstone): каждая функция → `void f_<va>(Ctx*)`; переходы → goto, внешние переходы и
  вызовы → `RecompDispatch`; `ret n` → `ret_target`; точные флаги; rep-строковые операции, `lock cmpxchg`
  (атомарно), SSE-скаляры, базовый x87 (double). Неподдержанное → явный `RecompUnimplemented`.
- Весь движок: ~2.49 млн инструкций, 186 мнемоник; top-100 покрывают 99.89%.
- Прототип: 177 функций (файловая система, память, мьютексы, запросы) → 0 неподдержанных инструкций.
- `src/recomp/runtime.h`: Ctx, память `base + 32-битный адрес` (база 0 в прототипе, на ARM64 — резерв 4 ГиБ).
- `src/recomp/bridge_x86.cpp`: мост внутри оригинального процесса (вход со сменой стека хоста, вызовы в
  нативный код с подменой адреса возврата, float-результат через st0, вложенность, состояние потока в fs:[0x14]).
- Режим `PROTORE_RECOMP=1`: хуки исполняют перекомпилированный код. Игра работает до меню, >4 млн входов за 90 с;
  все дифтесты проходят (14 304 проверки, 0 расхождений).
- Известные ограничения прототипа: SEH-исключение внутри перекомпилированного кода не обрабатывается (стек хоста
  вне границ стека потока в TIB); x87 считается в double (без 80-бит и без управляющего слова точности).
- Ручные реконструкции запросов (93) ещё без дифтестов → выключены; в режиме перекомпиляции вместо них работает
  перекомпилированный код.

## Перекомпилятор: полное покрытие инструкций и подготовка к сборке всего движка
- Разбор по потоку управления (таблицы переходов из образа, `int3`/данные внутри кода → ловушки).
- Полная модель x87 (стек, C0–C3, `fnstsw`/`lahf`/`sahf`, `fcomi`, точность/округление из управляющего слова,
  трансцендентные функции, 80-битные числа), упакованный SSE, `lock`-атомарность, `fs` через TEB, редкие инструкции.
- Весь движок: 73 595 функций, неподдержанных инструкций 0 (было 37 800).
- Анализ живости флагов (данные capstone + ручные поправки для `lahf`/`pushfd`/`fcomi`/`comiss`/`sahf`/`popfd`).
- `--split`: части по 400 функций + `table.c` (таблица функций и метаданные точек входа для 99.7% функций).
- `setjmp`/`longjmp` (Lua): host `setjmp` в кадре перекомпилированной функции, `longjmp` хоста; `_CxxThrowException`
  (1 место) и SEH (4 функции) пока нативные.
- Прямой тест: `PROTORE_DIFFTEST_RECOMP=1` перенаправляет ручные реконструкции на перекомпилированный код:
  14 304 проверки + 2 632 сценария, 0 расхождений (нашёл ошибку хвостового вызова в нативный код в мосте).
- Режим `PROTORE_RECOMP=all`: вход в перекомпилированный код у каждой функции движка.
- Оценка сборки всего движка по выборке: ~10 мин на 4 ядрах, ~77 МБ машинного кода.
